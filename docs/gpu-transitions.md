# File-based GPU transitions

Transitions are GPU packages under `transitions/`, using the same pipeline grammar as
[GPU effects](gpu-effects.md). The difference is that a transition pass gets **two** source
frames instead of one, plus `u_progress`.

Preview and export share one path: `FrameCompositor::drawTransitionFrame` → `GpuEffectExecutor`.

## Package layout

```
transitions/
└── plasma_burn/
    ├── transition.json
    ├── preview_strip.png   # optional; generated by tools/transitionthumbs
    └── main.frag
```

Search order: `DRIFT_TRANSITIONS_DIR`, `<applicationDir>/transitions`, `<AppDataLocation>/transitions`.

## transition.json

| Field | Meaning |
|---|---|
| `id` / `displayName` / `category` / `order` | Catalog metadata. **`id` is what gets serialized into project files** |
| `audioCurve` | `"crossfade"` (default, linear), `"dip"` (silent at the midpoint), `"hold"` (no ducking) |
| `previewStrip` / `previewFrames` | Optional. Defaults to `preview_strip.png`; frame count is inferred from the aspect ratio if omitted |
| `parameters[]` / `fixedParams` | Same as effects |
| `pipeline` | Same as effects, but `source_texture` accepts `"index": 0` (outgoing) or `"index": 1` (incoming) |

The nine ids carried over from the original enum — `crossfade`, `dip`, `dip_white`, `wipe_left`,
`wipe_right`, `wipe_up`, `wipe_down`, `push_left`, `zoom_in` — must keep those exact names, since
older project files already reference them.

## GLSL

Beyond the effect uniforms, every transition pass may declare:

| Uniform | Meaning |
|---|---|
| `u_fromTexture` | The outgoing clip (source index 0) |
| `u_toTexture` | The incoming clip (source index 1) |
| `u_progress` | `0..1` across the transition window |

Both sides arrive as **full-canvas RGBA layers** with the clip's transform, rotation, opacity,
fades, effects and mask already baked in, and transparent everywhere the clip isn't. Sample them
in straight alpha, and use `over()` when compositing rather than assuming opaque input.

`v_texCoord.y == 0` is the **top** of the frame. Sources are promoted into FBOs on upload and read
back unflipped, so this stays consistent across passes.

## The determinism rule

**A transition must be a pure function of `(fromTexture, toTexture, u_progress, parameters)`.**

The exporter renders frames independently and the user can scrub to any time, so a shader that
carries state between frames would make export disagree with the preview. Concretely:

- Derive every "random" term from `v_texCoord` and `u_progress` — **never** from `u_time` or
  `u_frameIndex`. To make glitches hold for a few frames, quantise progress
  (`floor(u_progress * 24.0)`), don't read the clock.
- Intermediate buffers are reallocated on every call. They are for multi-pass work *within* one
  frame, not for feedback across frames.
- Iterative looks (`liquid_smudge`, `particle_wind`) are built by running several passes in a
  single frame — e.g. `liquid_smudge` ping-pongs a warp field through `warpA`/`warpB` three times —
  never by accumulating between frames.

`EngineTest::transitionRenderingIsDeterministic` renders a frame, jumps forward, scrubs back, and
requires the two results to be bit-identical. It runs over every package in the catalog.

## Previews

```
./build/tools/transitionthumbs --transitions ./transitions --size 128 --frames 12
```

Renders N frames across `p = 0..1` through the real GPU path and packs them into one horizontal
strip. The browser rests on a mid frame and scrubs the strip on hover — a still at `p = 0.5` can't
distinguish a crossfade from a dip.

**Fallback:** if GL is unavailable, the package id is unknown, or the shader fails to compile, the
compositor falls back to a CPU crossfade — never a black frame.
